# AI Rules

This repository uses RojoTemplateV1.

## NON-NEGOTIABLE: refresh before every coding turn
Do not rely on chat memory, a previously-read tree, or an earlier ZIP.

Before editing code on EVERY coding turn:
1. Read the latest `ai-sync` branch.
2. Re-read this file from that branch.
3. Read `version.txt`, `default.project.json`, and every relevant file under `src/`.
4. Check the real current paths before deciding a file is new, renamed, moved, or deleted.

The user's local project is canonical. `ai-sync` is its latest GitHub mirror. Do not code from `main` when an `ai-sync` branch exists.

## Source of truth
- The user's local project is canonical.
- When working through GitHub, use the latest `ai-sync` branch, not `main`.
- `.build/`, `.tools/`, and `_versions/` are generated/runtime data. Do not edit or package them.
- `.rojo-template/STATE.json` is generated by the launcher. Do not hand-author it.

## Versioning
`version.txt` is one line:

`0.0.0_UpdateName`

Rules:
- `V1` is considered immutable once reached.
- `0.X.0` is reserved for a major system or notable milestone.
- `0.0.X` is for normal features, fixes, tuning, hotfixes, and other smaller changes.
- `UpdateName` must be very short.
- EVERY distributed AI code update MUST include a newly bumped `version.txt`, even when only one source file changed.
- Never reuse a version for different project contents.

## Mandatory delivery contract
When code was changed, the final response must:
- state the new version;
- briefly state what changed;
- explicitly mention any renamed/deleted files;
- provide the finished update ZIP as the primary deliverable;
- avoid dumping large replacement code blocks unless the user asks for them;
- never claim something was tested or verified unless it actually was.

Discussion-only/planning responses do not need an update ZIP.

## Update ZIP format
The ZIP is applied by copying/extracting its contents directly over the project root.

Normal ZIP contents:
```text
version.txt
<changed/new files at their exact project-relative paths>
```

If the update deletes or renames old source files, ALSO include:
```text
_AI_DELETE.txt
```

`_AI_DELETE.txt` rules:
- one exact project-relative path per line;
- only paths under `src/`;
- use forward slashes, for example `src/client/OldController.client.lua`;
- for a rename/move, list the OLD path and include the NEW file at its new path;
- never list a path that is also supposed to remain at that same path in the update;
- no wildcards;
- no absolute paths;
- no `..` traversal.

The launcher consumes `_AI_DELETE.txt` before hashing/building, performs the deletions safely, removes empty source folders, then deletes the manifest. This makes copy-over updates capable of real deletions instead of leaving stale scripts behind.

Package rules:
- Preserve exact project-relative paths.
- Do not place update files inside an extra wrapper folder.
- Never include `.build/`, `.tools/`, `_versions/`, or `.git/`.
- Do not include unchanged files merely to make the ZIP look complete.
- Include every dependent changed file needed for the update to work; do not deliver a knowingly partial patch.

## Before delivering
Verify the patch against the latest `ai-sync` tree:
- every intended changed/new file is present in the ZIP;
- every intended source deletion/rename is represented in `_AI_DELETE.txt`;
- no stale old path was accidentally kept;
- no path appears both as a deletion and as a file that should remain;
- `version.txt` is bumped and formatted correctly;
- the ZIP has no extra top-level wrapper directory.

## Project hash
The launcher computes ONE deterministic SHA-256 project hash from:
- `default.project.json`
- every file under `src/`, including relative paths

A changed, added, deleted, renamed, or edited source file changes the single project hash.
